# FeatureFlagSmasher — FeatureFlagLite

Build a **minimal, clean, production-style Feature Flag and Configuration Service** called **FeatureFlagLite**, inspired by the core concept of **Flagsmith**, but intentionally simplified for a small academic/project implementation.

## 1. Project Goal

FeatureFlagLite allows developers to:

* Create feature flags.
* Define a flag's name, description, and default state.
* Maintain independent flag states for **dev, test, and prod** environments.
* Read all feature flag states through an API for a specific environment.
* Track who changed a flag, what changed, and when.
* Support **percentage rollout from 0–100%** for gradual feature enablement.
* Provide a small test website/application that consumes the API and demonstrates the feature flags.

The implementation should prioritize **simplicity, maintainability, performance, clean architecture, validation, error handling, caching, and meaningful naming**.

## 4. Main Features

### Feature Flag Management

Implement APIs to:

* Create a feature flag.
* Get a feature flag.
* Get all feature flags.
* Update a feature flag.
* Delete a feature flag.

Creation should require:

* Name
* Description
* Default state

Validate that flag names are:

* Required
* Non-empty
* Meaningful
* Unique

---

### Environment-Specific Configuration

A feature flag must be independently configurable for:

```text
dev
test
prod
```

Example:

```text
newDashboard
    dev  -> ON
    test -> ON
    prod -> OFF
```

Changing one environment must not modify the others.

---

### Percentage Rollout

Support gradual rollout:

```text
0%   -> Disabled
25%  -> Enabled for approximately 25% of users
50%  -> Enabled for approximately 50% of users
100% -> Fully enabled
```

Store rollout as an integer between `0` and `100`.

For the read/evaluation API, allow an optional user identifier such as:

```text
?userId=123
```

Use a deterministic hashing approach so the same user consistently receives the same result for the same flag.

Avoid random evaluation on every request.

## 5. Read API

Provide a simple API for client applications to retrieve feature flags for an environment.

Example:

```http
GET /api/v1/flags?environment=dev
```

Response:

```json
{
  "environment": "dev",
  "flags": {
    "newDashboard": true,
    "darkMode": false,
    "newCheckout": true
  }
}
```

Also provide an evaluation API:

```http
GET /api/v1/flags/{flagName}/evaluate?environment=dev&userId=123
```

Response:

```json
{
  "flagName": "newDashboard",
  "environment": "dev",
  "enabled": true,
  "rolloutPercentage": 50
}
```

Keep read operations lightweight and optimized because they may be called frequently by client applications.

## 6. Change History

Whenever a flag's environment-specific state changes:

* Record the previous state.
* Record the new state.
* Record the environment.
* Record the user who made the change.
* Record the timestamp.

Example:

```text
Flag: newDashboard
Environment: prod
Changed By: admin
Old State: OFF
New State: ON
Old Rollout: 0
New Rollout: 50
Changed At: 2026-09-28 10:30:15
```

Provide an API to retrieve change history:

```http
GET /api/v1/flags/{flagName}/history
```

## 12. Caching

Optimize frequent read operations using Spring Cache.

Cache:

* Environment-specific flag states.
* Frequently requested flag evaluations.

Example cache key:

```text
flags:dev
flags:test
flags:prod
```

Invalidate or refresh the relevant cache whenever a flag state changes.

Do not return stale data after an update.

Keep the caching implementation simple and suitable for a single-instance application.

## 13. Database Optimization

Use MySQL with proper indexes and constraints.

Important constraints/indexes:

```text
FeatureFlag.name          UNIQUE
Environment.name         UNIQUE
(featureFlagId, environmentId) UNIQUE
```

Use:

* Lazy relationships where appropriate.
* Pagination for history APIs when needed.
* Efficient queries.
* Avoid N+1 query problems.
* Avoid unnecessary database calls.
* Use transactions for flag-state updates and change-log creation.

Do not over-engineer the database.

---

## 14. Performance and Complexity

Keep the application lightweight.

Requirements:

* Read APIs should minimize database access.
* Use caching for frequently requested configuration.
* Percentage rollout evaluation should be deterministic and approximately `O(1)`.
* Avoid unnecessary object creation.
* Avoid loading full entity graphs for simple API requests.
* Use projections or optimized queries where useful.
* Keep API responses small.

Do not introduce unnecessary microservices or complex infrastructure.
